# astock Web 选股工作台设计

## 背景

当前 `astock` 以 CLI 为主要交付形态，核心业务能力已经沉淀在 `ScreeningEngine`、可插拔数据源、可插拔存储和策略插件层中。

仓库架构已经为 Web 扩展预留了位置，但尚未提供可直接使用的 Web 工作台。

本次目标是为项目补齐一个“本地单机优先、前后端分离、后续可部署”的 Web 交付层，让用户可以通过页面配置参数、触发选股、查看结果、查看个股详情和回看运行历史。

## 目标

- 提供一个可直接运行的 Web 选股工作台
- 采用前后端分离目录，保证代码边界清晰
- 后端复用现有 `ScreeningEngine` 和配置体系，不重写选股核心逻辑
- 前端提供参数配置、结果表格、详情图表和运行历史四类核心能力
- 首版以本地单机使用为主，不引入登录与权限
- API 形态保留后续异步任务和部署扩展空间

## 非目标

- 不实现用户系统、权限控制和多人协作
- 不实现定时调度、消息推送和实时通知
- 不支持在线新增策略实现，只支持对已注册策略进行启停和参数调整
- 不实现复杂分析看板或跨运行统计分析
- 不替代现有 CLI，CLI 仍然保留并继续作为核心回归路径

## 方案选择

已确认采用“前后端分离”方案。

选择原因：

- 更符合“在合适目录下维护前后端代码”的诉求
- 更适合承载参数工作台、结果表格、详情图表、历史页等中等复杂度交互
- 保持后端 API 与前端页面职责分离，便于后续部署
- 不要求立即改造现有引擎边界，风险更可控

未采用的方案：

- 服务端模板渲染方案：首版更快，但图表与复杂交互的演进空间偏小
- 快速原型方案：出活快，但后续大概率需要推倒重来

## 总体架构

采用三层结构：

- 核心业务层：现有 `src/astock/` 中的数据源、存储、策略、引擎、配置
- Web 后端层：新增 `src/astock/webapi/`，对外暴露 HTTP API，并复用核心业务层
- Web 前端层：新增 `frontend/`，负责页面、路由、状态管理、图表和 API 调用

核心原则：

- Web 后端是新的交付层，不是新的选股引擎
- `ScreeningEngine` 继续承担核心编排职责
- 策略层仍只依赖 `StrategyContext`，不感知 Web 请求
- 运行历史是交付层能力，不污染现有 `Repository` 抽象边界

## 页面范围

首版页面能力包含以下四部分。

### 1. 运行工作台

用于配置并触发一次选股运行。

包含：

- 配置文件选择
- 数据源与存储选择
- `limit`、`kline_days`、`min_score` 等运行参数
- 策略启停与策略参数编辑
- 运行按钮和运行状态摘要

### 2. 结果列表

用于展示本次运行的股票结果列表。

包含：

- `rank`
- `code`
- `name`
- `board`
- `total_score`
- 各策略分数
- 原因摘要

支持：

- 排序
- 关键字筛选
- 点击行进入详情

### 3. 个股详情

用于查看单只股票在本次运行中的结构化结果。

包含：

- 基础信息
- 总分与各策略分数
- 策略解释明细
- K 线数据
- 技术指标数据
- 资金流数据

### 4. 运行历史

用于回看过去运行的参数和结果。

包含：

- 运行时间
- 参数快照
- 结果数量
- Top N 摘要
- 历史结果回看入口

## 后端 API 设计

### 元数据接口

- `GET /api/meta/options`
  - 返回数据源列表、存储列表、策略列表、默认配置和前端初始化所需元数据

元数据来源：

- 数据源列表来自 `list_providers()`
- 存储列表来自 `list_repositories()`
- 策略列表来自 `list_strategies()`
- 默认值来自 `config/default.yaml`

### 运行接口

- `POST /api/runs`
  - 提交一次运行请求
- `GET /api/runs/{run_id}`
  - 返回运行状态、参数快照和摘要信息
- `GET /api/runs/{run_id}/results`
  - 返回结果列表
- `GET /api/runs/{run_id}/results/{code}`
  - 返回单只股票详情

### 历史接口

- `GET /api/history`
  - 返回历史运行列表
- `GET /api/history/{run_id}`
  - 返回某次历史运行的完整快照

## API 模型约束

后端应显式定义请求和响应模型，避免前后端口头约定字段。

首版至少定义以下模型：

- `RunRequest`
- `RunSummary`
- `RunStatusResponse`
- `ResultItem`
- `ResultDetail`
- `HistoryItem`
- `HistoryDetail`
- `ApiError`

状态字段统一使用：

- `pending`
- `running`
- `succeeded`
- `failed`

## 数据流设计

### 初始化

前端启动后先请求 `GET /api/meta/options`，获取表单元数据与默认配置。

### 发起运行

用户在工作台调整参数后，前端调用 `POST /api/runs` 提交运行请求。

后端处理流程：

1. 校验请求参数
2. 将前端请求映射为运行时配置对象
3. 创建 `run_id`
4. 写入运行记录初始状态
5. 调用 `ScreeningEngine.run()`
6. 保存结果快照与运行摘要
7. 返回状态给前端

### 获取结果

前端随后请求：

- `GET /api/runs/{run_id}`
- `GET /api/runs/{run_id}/results`

用户点击某只股票后，再请求：

- `GET /api/runs/{run_id}/results/{code}`

### 历史回看

前端通过：

- `GET /api/history`
- `GET /api/history/{run_id}`

完成历史列表与单次历史详情展示。

## 运行模式设计

首版按同步运行设计，前端在发起运行后展示 loading 和阶段状态。

同时保留异步升级空间：

- 接口保留 `status`
- 运行记录从一开始就有状态机
- 前端状态机不假设“请求返回即完成”

这样后续如果要升级为后台任务，不需要推翻页面和接口形态。

## 运行历史设计

历史记录存储于 Web 层，不直接修改现有 `Repository` 抽象接口。

保存内容：

- `run_id`
- 创建时间
- 参数快照
- 运行状态
- 结果摘要
- 结果快照

设计原则：

- 历史列表仅返回摘要，避免大 payload
- 历史详情按需返回完整内容
- 历史回看基于快照，不依赖重新拉取外部行情数据

## 结果与详情建模

列表接口与详情接口分离：

- 列表接口保持轻量，适合结果表格渲染
- 详情接口返回结构化数据，适合详情页与图表展示

详情接口建议返回：

- 股票基础信息
- 本次总分
- 各策略分数
- 各策略 `passed`、`score`、`reason`、`details`
- K 线序列
- 指标序列
- 资金流序列

后端应避免仅返回拼接字符串形式的原因说明，尽量透出结构化字段供前端渲染。

## 前端状态管理

状态划分为三类。

### 配置态

保存：

- 当前表单值
- 默认值
- 是否已修改
- 校验结果

要求：

- 页面切换后不丢失用户未提交的配置

### 运行态

保存：

- `run_id`
- 当前运行状态
- 错误信息
- 当前结果列表
- 当前选中股票详情

要求：

- 新运行开始时，旧结果可短暂保留，直到新结果完成返回

### 历史态

保存：

- 历史列表
- 当前查看的历史详情

要求：

- 查看历史时不覆盖当前配置态

## 错误处理

错误分为三类。

### 参数校验错误

示例：

- 类型错误
- 阈值越界
- 参数缺失

处理：

- 后端返回 `400`
- 前端在表单区域展示字段级错误

### 业务运行错误

示例：

- 未启用任何策略
- 数据源未注册
- 存储初始化失败

处理：

- 后端返回 `4xx/5xx`
- 前端在运行区展示失败态
- 保留用户刚才填写的参数

### 数据缺失与局部失败

示例：

- 某只股票 K 线缺失
- 资金流接口失败

处理：

- 整次运行不直接失败
- 复用当前引擎容错语义
- 前端对局部缺失做降级展示

## 测试策略

测试分为三层。

### 后端测试

重点覆盖：

- 元数据接口
- 运行接口请求映射
- 结果列表接口
- 详情接口
- 历史保存与查询

测试方式：

- 复用 `MockProvider + 内存 SQLite`

### 前端测试

重点覆盖：

- 参数表单渲染与校验
- 运行状态切换
- 结果表格展示
- 详情页数据适配
- 历史回看流程

原则：

- 优先覆盖高风险交互
- 避免为纯样式细节编写低价值测试

### 端到端测试

覆盖最小闭环：

1. 配置参数
2. 发起运行
3. 查看结果
4. 打开详情
5. 查看历史

现有 `python3 tests/test_e2e.py` 继续保留，用于保障 CLI 与引擎主流程不被 Web 接入破坏。

## 实现计划

### 阶段 1：后端 API 骨架

- 新增 `src/astock/webapi/`
- 接入 FastAPI
- 建立健康检查、元数据接口、运行接口、结果接口骨架
- 定义统一 schema 和错误模型

### 阶段 2：运行历史与详情能力

- 增加运行历史存储
- 保存参数快照与结果快照
- 补齐详情接口

### 阶段 3：前端工作台闭环

- 新增 `frontend/`
- 完成工作台布局
- 完成参数面板
- 完成结果表格
- 接通后端 API

### 阶段 4：图表与历史页

- 完成个股详情图表
- 完成运行历史页
- 补齐空态、错误态、加载态

## 建议实施顺序

1. 先完成后端 `meta + runs + results`
2. 再完成前端工作台与结果表格
3. 然后补齐历史与详情能力
4. 最后补图表与交互优化

该顺序可以保证任意中间阶段都保留一个可运行、可验证的版本。

## 风险与对策

### 风险 1：前端参数模型与后端配置映射不一致

对策：

- 先定义显式 schema
- 单独实现请求到 `Settings` 的映射器

### 风险 2：详情页所需字段当前结果中缺失

对策：

- 使用独立详情接口
- 由后端负责补齐结构化详情数据

### 风险 3：运行时间较长影响体验

对策：

- 首版接受同步执行
- 但前后端状态机按异步可升级方式设计

### 风险 4：历史快照体积过大

对策：

- 历史列表只返回摘要
- 详情内容按需获取

## 验收标准

- 本地可同时启动前后端
- 页面可编辑参数并发起一次选股运行
- 页面可查看结果列表
- 页面可查看单只股票详情和图表
- 页面可查看至少一次历史运行记录
- 不破坏现有 CLI 主流程和端到端测试路径
